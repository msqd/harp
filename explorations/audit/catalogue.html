Ce que l'audit enregistre

L'audit couvre le plan de contrôle : ce qu'un account fait à HARP, et les accès que HARP accorde de lui-même. Chaque événement est écrit dans le même commit que l'action, puis copié dans le logger harp.audit. Les refus sur les actions critiques y figurent ; les lectures, le trafic et les comportements automatiques n'y figurent pas.

succeeded l'action a eu lieu failed tentée, mais elle a échoué (mauvais mot de passe, erreur) denied refusée faute de rôle (403)

Un refus (denied) reprend le nom de l'action refusée, avec required_role dans le détail. On lit ainsi au même endroit « Bob a tenté de se donner le rôle Admin » et « Alice a donné le rôle Admin à Bob ».

Dans les logs seulement

Ces événements sont déclarés loggable par l'app qui les émet. Ils partent, au mieux et sans transaction, dans le logger harp.events, et l'Operator peut faire taire chacun d'eux. Un événement non déclaré ne va ni en audit ni en log ; les événements du trafic ne sont jamais déclarés.

Ce qui n'est pas enregistré

QuoiPourquoi
Les lectures, y compris les lectures refuséesUn Viewer qui ouvre une transaction, ou qui tombe sur un 403 en ouvrant la page des settings, n'a rien changé. Ces lectures se comptent en milliers par jour.
Chaque requête authentifiée par jeton ou par Basiclast_used_at suffit. Les échecs vont dans les logs (auth.sign_in_failed).
Les expirations de session, de jeton ou d'invitationPersonne n'a agi. L'état se lit dans les tables d'auth.
Les favorisCe sont les préférences personnelles d'un compte, pas des actions sur HARP.
Les requêtes MCPCe sont des lectures. Les quotas d'explore/mcp les comptent ailleurs.
Le trafic, PURGE comprisIl passe par le proxy, et c'est le Transaction Record qui le garde.

La forme d'un événement

ChampSens
id, occurred_atIdentifiant croissant et horodatage UTC.
action, outcomeLe nom de l'action dans le catalogue, et son résultat.
actor_account_idL'account qui agit. Vide quand c'est le système qui agit, par exemple pour l'invitation de setup.
actor_via, actor_via_idsession, token, cli ou system, avec l'id de la session ou du jeton. Plus tard access_token, pour un agent MCP passé par OAuth.
actor_clientLe client par lequel l'account agit, quand on le connaît. Par exemple, un agent MCP.
ip, user_agentD'où vient la requête.
target_type, target_id, target_labelSur quoi porte l'action. Le label est recopié (le username, le nom du jeton) pour rester lisible après une suppression.
detailsUn JSON court, propre à chaque action (dernière colonne du catalogue). Il ne contient jamais de secret.
